# KBL 실시간 승률 예측 시스템 - 원본 데이터 수집

카드게임(kbl540 등)과는 별개 프로젝트. **실제 KBL 정규리그 경기**의 문자중계/박스스코어를 모아서
라인업 시너지·매치업 효과를 학습하는 AI 승률 예측 시스템을 만드는 게 목표. (2026-08-19 시작)

## 현재 상태 (2026-08-19 기준, 15시즌 수집 완료)

- **4,207경기** 수집 완료 (2011-12~2025-26, 15시즌, 정규시즌+플레이오프, 실패 0건). 원래 5시즌
  (2021-22~)만 있었는데 사용자 요청으로 10시즌 더 확장(2011-12~2020-21) - 처음엔 `--from-date`
  기본값을 안 바꿔서 최근 시즌 하나만 들어가는 실수가 있었고, 바로잡아 재수집함
- 라인업 스틴트 재구성 **4,155/4,207(98.8%) 득점 검증 통과**. 불일치 52건 중 상당수가 한 경기
  (`S27G01N106`)에 몰려있음 - 그 경기 문자중계에 선수 한 명(임재현)이 박스스코어 로스터와
  안 맞는 케이스, KBL 원본 데이터 자체의 이례적인 사례로 추정
- SQLite 적재 완료: `player_game_stats` 100,921건, `shot_log` 553,248건, `lineup_stints` 110,147건
- **경기 전 예측 - 여러 모델 하이퍼파라미터 튜닝 결과** (15시즌 전체, 2025-26 시즌 홀드아웃 기준):

  | 모델 | 정확도 | 로그손실 |
  |---|---|---|
  | **RandomForest** | **62.9%** | 0.670 |
  | LogisticRegression | 61.8% | **0.666** (최고 확률보정) |
  | XGBoost | 61.5% | 0.672 |
  | HistGradientBoosting | 60.8% | 0.675 |

  베이스레이트(55.4%) 대비 전부 유의미하게 개선. 5시즌(1,400행)일 때보다 데이터가 3배(4,182행)로
  늘고 시즌경계 기준 CV 폴드도 2개→12개로 늘면서 모델 간 격차가 좁혀짐(60.8~62.9%, 이전엔
  54.8~62.5%) - 특히 로지스틱회귀가 튜닝+데이터 확장으로 59.7%→61.8%까지 크게 개선됨.

## kbl.or.kr 비공식 API

사이트가 SPA라 HTML엔 데이터 없음. 내부적으로 `api.kbl.or.kr`을 호출하는데 **인증/쿠키/토큰 전혀
불필요** - 아래 3개 정적 헤더만 있으면 curl로도 그대로 받아짐. robots.txt도 명시적 차단 없음
(koreabaseball.com과 다름 - 거긴 크롤링 금지, 여긴 아님).

```
Channel: WEB
TeamCode: XX
lang: ko
```

### 엔드포인트

| 엔드포인트 | 내용 |
|---|---|
| `GET /match/list?fromDate=YYYYMMDD&toDate=YYYYMMDD&tcodeList=all` | 기간별 경기 목록 (gmkey, 날짜, 홈/원정, 스코어, 시즌코드, 시즌카테고리) |
| `GET /match/year` | 시즌 연도 목록 (1997~2027 나열됨, 실제 데이터는 최소 2015시즌까지 확인됨) |
| `GET /match/{gmkey}` | 경기 메타 (팀, 감독/코치, 쿼터별 스코어, 심판, 구장, 관중수) |
| `GET /match/{gmkey}/player-stat` | 선수별 **경기단위** 박스스코어 - 1,2차 스탯 + 출전시간(분초) + 선발여부(startFlag) + PER/ORTG/DRTG 등 |
| `GET /match/{gmkey}/team-record` | 팀 단위 경기 기록 |
| `GET /match/{gmkey}/match-chart` | 슛차트 - 선수별 슛 시도 x/y좌표, 쿼터, 성공여부, 2점/3점 구분 |
| `GET /match/{gmkey}/text-cast` | **문자중계 이벤트 로그** - 시간(분:초), 선수명, 팀코드, 쿼터, 액션코드(`a`) - 라인업 재구성의 핵심 |

`gmkey` 형식: `S{시즌코드}G{게임코드}N{당일경기번호}` (예: `S47G14N1` = 47번째 시즌 14회차 첫 경기).
`seasonCategory`: R=정규시즌, PO=플레이오프, CU=컵대회, AS=올스타, OM=오픈매치데이(프리시즌),
D1/D2=D리그(2군), EA=동아시아 슈퍼리그. **현재 수집 대상은 R+PO만** (2군/이벤트성 경기 제외).

15연속 요청 테스트에서 차단/제한 없었음. 그래도 예의상 요청 사이 0.35초 딜레이 넣음
(`fetch_kbl_data.py`의 `DELAY_SEC`).

### 문자중계 액션 코드 매핑

`tools/kbl_action_codes.json` - 사이트 프론트엔드 JS 번들(`index-DRtx4Fny.js`)에서 원본 그대로
추출한 공식 매핑표 (`gameActionCodeList`/`gameFoulCodeList`/`gameChangeCodeList`/`quaterList`).
역추적 안 하고 소스에서 직접 가져온 거라 정확함 - 실제 경기(S47G14N1) 이벤트로 검증 완료
(교체 순서가 UI에 표시된 문자중계와 완전히 일치).

주요 코드: `101`=교체(IN), `102`=교체(OUT), `201`=2점슛성공, `205`=3점슛성공, `203`=자유투성공,
`209`/`210`=공격/수비리바운드, `211`=어시스트, `212`=스틸, `213`=블록, `214`=턴오버, `216`=파울.
전체 34개 코드는 JSON 파일 참고.

## ⚠️ text-cast는 반드시 quarterList 파라미터 필요

`GET /match/{gmkey}/text-cast` 를 파라미터 없이 부르면 **서버가 마지막 쿼터 이벤트만** 돌려준다
(문자중계 탭의 기본/라이브 동작 - 진행중 경기에서 "현재" 보여주기 위한 서버 기본값으로 추정).
전체 경기를 받으려면 프론트 JS 번들에서 확인한 실제 파라미터로 명시 요청해야 함:

```
GET /match/{gmkey}/text-cast?quarterList=Q1,Q2,Q3,Q4,X1,X2,X3,X4
```

(X1~X4 = 연장 1~4쿼터. 연장 없는 경기엔 그냥 무시됨.) `fetch_kbl_data.py`는 이미 이렇게 고쳐놨음.
**2026-08-19 처음 수집했을 때 이 파라미터를 안 넣어서 문자중계가 전부 마지막 쿼터만 잘려 들어간
적 있음 - 스틴트 재구성 후 득점 합계가 실제 스코어와 안 맞아서 발견함.** 문자중계 관련해서 뭔가
이상하면 이 파라미터부터 의심할 것.

## 라인업 stint 재구성 - 완료

`tools/build_lineup_stints.py` - 문자중계 이벤트를 순서대로 재생하면서 교체(101=IN/102=OUT)마다
스틴트를 끊고, 그 구간 각 팀 득점을 기록. 득점 코드는 `201`(2점) `205`(3점) `203`(자유투)
`207`(덩크 - 201과 별도 코드라 빠뜨리기 쉬움, 실제로 한 번 빠뜨렸다가 스코어 검증에서 걸림)
4개 다 합산해야 함. 같은 (쿼터,시각)에 동시에 여러 명 교체되는 경우(쿼터 시작/막판 대량교체)는
한 배치로 묶어서 처리 - 안 그러면 0점짜리 찰나의 스틴트가 우수수 생김. 쿼터 경계에서
"전원 OUT(이전쿼터 시각) → 전원 IN(다음쿼터 시각)"이 서로 다른 배치로 찍히는 것도 빈 스틴트로
걸러냄.

검증: 스틴트별 득점 합계 == 실제 최종 스코어를 경기마다 자동 체크(`build_game_stints`의
`validation` 필드). 지금까지 테스트한 경기는 전부 정확히 일치.

```bash
python build_lineup_stints.py --gmkey S39G01N1   # 경기 하나만
python build_lineup_stints.py                    # raw/games 전체 처리
```

출력: `raw/stints/{gmkey}.json` - 스틴트 배열(홈/원정 5인 pcode, 쿼터, 시작/끝 시각, 득점).

## 시너지 · 매치업 분석 엔진 - 완료 (1차)

`tools/build_synergy_matchup.py` - `raw/stints/*.json`을 스틴트 단위로 묶어서 계산:

- **온/오프코트 net rating**: 선수가 코트에 있을 때 팀 득실차를 40분 기준으로 환산
- **2인/3인 조합 시너지**: N명이 동시에 코트에 있었던 스틴트만 모아 같은 방식으로 계산
- **매치업**: 우리 선수 A가 상대 선수 B와 동시 출전했던 스틴트를 모아 그 구간 net rating 계산

**중요한 한계**: 매치업은 실제 1대1 수비 배정이 아니라 "동시 출전(co-occurrence)" 기준 근사치임 -
문자중계에 개별 수비 매칭 정보가 없어서 낼 수 있는 최선. 표본이 적은 조합(몇십 초)은 노이즈가
커서 `--min-onoff-sec`/`--min-combo-sec`로 최소 표본을 거른다(기본 300초/180초).

953경기 기준 첫 실행 검증: 모리구치 히사시(138분, 106스틴트) +15.05 처럼 표본 큰 선수는
안정적인 값, 표본 작은 선수는 예상대로 노이즈 큰 값(±20 이상) - 정상적인 plus-minus 특성.

```bash
python build_synergy_matchup.py   # raw/analysis/player_onoff.json, combo_2man.json, combo_3man.json, matchups.json
```

## 일일 배치 - 스케줄러 등록 완료 (2026-08-24)

`tools/daily_batch.py` - 매일 실행되는 스크립트. 어제~오늘 날짜 범위에서 새로 끝난 경기
(`isEnded:1`)만 찾아 수집 + 스틴트 재계산까지 한 번에 처리. 하루 여러 번 돌려도 안전(이미
받은 파일은 건너뜀). 시즌 개막 전(지금)엔 매일 "새로 끝난 경기 없음"만 찍고 조용히 끝남 -
10월 개막하면 자동으로 수집 시작.

```bash
python daily_batch.py                 # 어제~오늘 (매일 새벽 크론용)
python daily_batch.py --date 20261015 # 특정 날짜 재처리
```

**Windows 작업 스케줄러 `KBL_DailyBatch` 태스크로 등록함** - 매일 06:00 실행, 컴퓨터가 그
시각에 꺼져있었으면 켜지는 대로 따라잡음(`-StartWhenAvailable`). 등록 과정에서 함정 두 개
발견:
1. 경로에 한글이 섞여있어서 `.bat` 파일로 감싸면 cmd.exe가 파일을 시스템 기본 코드페이지
   (cp949)로 잘못 읽어 경로가 깨짐("지정된 경로를 찾을 수 없습니다") - **파일이 아니라 명령줄
   인자로 직접 넘기면** OS가 유니코드로 그대로 전달해서 안 깨짐.
2. 파이썬이 콘솔 없이 리다이렉트될 때 stdout을 UTF-8이 아니라 시스템 코드페이지로 내보내서
   로그 파일이 깨졌음 - `python.exe -X utf8`로 강제 UTF-8 모드를 줘서 해결.

최종 태스크 액션(작업 디렉터리: `tools/`):
```
cmd.exe /c ""...\.venv\Scripts\python.exe" -X utf8 daily_batch.py >> "...\raw\daily_batch.log" 2>&1"
```

Task Scheduler를 통해 실제로 트리거해서 exit code 0 + 정상 UTF-8 로그 출력까지 확인 완료.
로그는 `raw/daily_batch.log`에 계속 누적됨.

```powershell
Get-ScheduledTask -TaskName "KBL_DailyBatch"                          # 상태 확인
Get-ScheduledTaskInfo -TaskName "KBL_DailyBatch"                       # 다음/마지막 실행, 결과코드
Start-ScheduledTask -TaskName "KBL_DailyBatch"                         # 수동 즉시 실행
Unregister-ScheduledTask -TaskName "KBL_DailyBatch" -Confirm:$false    # 삭제
```

## 경기 전(pre-game) 예측 피처 테이블 - 완료 (1차) + 베이스라인 검증

`tools/export_training_table.py` - 팀별 **직전 최대 10경기 이동평균**(offrtg/defrtg/netrtg/pace 등)으로
경기 전 시점 피처를 만든다. **데이터 누수 방지가 핵심**: 그 경기 당일/이후 스탯은 절대 포함 안 하고
무조건 그 경기 이전 날짜의 경기들만 사용. 직전 경기 3경기 미만(시즌 극초반)인 행은 제외.

검증 결과(1,400행, 전체 5시즌): 홈팀 베이스레이트 승률 54.6%(실제 KBL 홈어드밴티지와 부합) 대비,
`home_netrtg - away_netrtg` 딱 한 개 피처로 만든 단순 임계값 규칙이 **62.2%** 정확도 - 실제 모델도
아니고 피처 엔지니어링도 없는 규칙 하나인데 베이스레이트를 유의미하게 이김. 파이프라인 전체
(수집→스틴트→팀레이팅→롤링피처)가 실제 예측 신호를 담고 있다는 증거.

```bash
python export_training_table.py   # raw/analysis/pregame_training_table.json
```

### 여러 모델로 재비교 (2026-08-19, 사용자 요청) - 비선형 모델에서는 신체정보도 도움됨

`tools/compare_models.py` - scikit-learn/xgboost 설치(`.venv`에 새로 추가, 이 스크립트만 필요)해서
로지스틱회귀·랜덤포레스트·그래디언트부스팅(sklearn)·HistGradientBoosting·XGBoost 5개 모델을
4개 피처셋에 전부 돌려봄(20개 조합). **결측치를 0으로 채우지 않고 NaN 그대로 둠** - 트리 모델은
결측 자체를 분기 조건으로 학습할 수 있어서, 로지스틱회귀에서 신체정보가 해가 됐던 게 "0으로
억지로 채운 탓"이었는지 여기서 확인됨. 평가는 동일하게 2025-26 시즌 홀드아웃.

**상위 5개 조합** (전체 20개는 `raw/analysis/model_comparison.json`):

| 순위 | 피처셋 | 모델 | 정확도 | 로그손실 | AUC |
|---|---|---|---|---|---|
| 1 | everything | **RandomForest** | **62.5%** | 0.675 | 0.608 |
| 2 | team-stats+synergy | RandomForest | 61.8% | 0.674 | **0.611** |
| 3 | team-stats | RandomForest | 60.1% | 0.685 | 0.579 |
| 4 | team-stats+synergy | LogisticRegression | 59.7% | 0.673 | 0.622 |
| 5 | everything | GradientBoosting(sklearn) | 59.7% | 0.681 | 0.600 |

**핵심 발견**: RandomForest가 모든 피처셋에서 가장 강력했고, **RandomForest에서는 신체정보/컴바인
데이터가 실제로 도움이 됨** (everything 62.5% > team-stats+synergy 61.8% > team-stats 60.1%) -
로지스틱회귀에서 신체정보가 해가 됐던 건 데이터 자체가 무의미해서가 아니라 "단순 선형모델 +
팀단위 평균 + 0-대입"이라는 조합의 한계였다는 게 확인됨. 트리 모델은 결측/비선형 상호작용을
더 잘 다룸.

**의외의 결과**: 정작 사용자가 물어본 "그래디언트부스팅/XGBoost" 계열(GradientBoosting,
HistGradientBoosting, XGBoost)은 RandomForest보다 대체로 낮았고 몇몇 조합에선 로지스틱회귀보다도

보통 대량 데이터에서 강점을 보임). 하이퍼파라미터 튜닝은 아직 안 했음 - 지금은 "기본값에
가까운 설정으로 5개 모델을 공정하게 비교"가 목적이었고, 최적화는 다음 단계.

### `tools/tune_hyperparams.py` - 시즌 경계 기준 확장윈도우 CV

`compare_models.py`(기본 하이퍼파라미터로 5개 모델 비교)의 다음 단계 - `RandomizedSearchCV`로
실제 튜닝을 하되, **무작위 K-fold 대신 시즌을 하나씩 늘려가며 다음 시즌을 검증하는 CV**를 씀
(과거로 학습해서 미래를 맞추는 실제 상황과 동일한 구조 - 무작위 K-fold는 같은 시즌 팀 전력이
train/val에 새서 튜닝 자체가 과최적화될 위험이 있음). **최종 홀드아웃(2025-26 시즌)은 튜닝 CV
풀에서 완전히 제외**하고 튜닝 끝난 뒤 딱 한 번만 평가 - 안 그러면 "튜닝해서 좋아진 성능"이
홀드아웃에 대한 은근한 과최적화일 수 있음.

5시즌만 있을 때는 CV 폴드가 2개뿐이라 튜닝 자체가 불안정했음(그래서 드라이런 결과는 참고만).
15시즌으로 늘면서 CV 폴드가 **12개**로 늘어 훨씬 신뢰할 수 있는 튜닝이 됨.

실제 금액 데이터는 없음.

### 나이-기량 곡선 + 생존편향 검증 (2026-08-20, 사용자 요청)

`tools/build_age_curves.py` - "가드는 나이 들수록 어시스트가 늘고 덩크는 주는가" 확인. NBA/일본/
중국 데이터는 안 빌림 - 3시즌 이상 뛴 선수가 432명이나 있어서 KBL 자체로 충분했고, 리그 간
신체조건·스타일 차이 보정 문제를 피할 수 있었음. Delta 방법(같은 선수의 연속 시즌 변화량만
모아 나이순 누적 - 세이버메트릭스 표준 기법) 사용.

결과: 가드/포워드/센터 전부 **어시스트율은 29~32세까지 상승**(BQ 축적), **덩크·블록은 20대
초반 정점 후 하락**(순수 운동능력), **3점슛은 포워드/센터가 나이 들수록 계속 상승**(스트레치
빅 전환). 사용자가 제시한 가설과 정확히 일치.

**⚠ 생존편향 재검증 (사용자 지적)**: delta 방법도 "34세까지 충분출전 유지"라는 조건 자체가
이미 선별된 표본이라 생존편향을 완전히 없애지 못함. `tools/check_survivorship_bias.py`로 직접
확인:
1. **나이별 생존율에 실제 절벽이 있음** - 20대 초반 70~80%에서 25~26세에 **43%까지 급락**,
   그 고비를 넘긴 선수는 이후 60~70%대로 안정
2. **국적 통제 시 장기생존자(8시즌+)가 데뷔 시즌부터 이미 더 나음** - 국내선수 기준 데뷔 PER
   12.89 vs 단기생존자 9.67 (처음엔 반대로 나왔는데, 단기생존자 그룹에 외국선수가 46%나 섞여
   있어서 생긴 착시였음 - 외국선수는 원래 데뷔부터 고사용률 스타로 기용돼서 PER이 높게 나오고,
   KBL 특성상 외국선수는 연 단위로 많이 교체되니 단기생존자에 쏠려있었던 것)
3. **장기생존자만으로 곡선을 다시 그리면 일부(가드 리바운드율·블록·3점슛)는 정점이 더 늦게
   나옴** - 원래 곡선의 "말년 반등"이 부분적으로 생존편향 때문일 가능성. 다만 득점/PER/턴오버율은
   코호트를 좁혀도 정점이 거의 안 바뀜 - 순수 개인성장 효과도 섞여있는 것으로 보임

**결론**: 둘 다 맞다 - 개인 성장과 생존편향이 섞여있고 현재 방법으론 완전히 못 나눔. 이 곡선을
예측 피처로 쓸 땐 "평균 선수의 성장 궤적"이 아니라 "**리그에 남은 선수들의 궤적**"으로 해석해야
함. 아직 실제 예측 파이프라인에는 결합 안 했음.

```bash
python build_age_curves.py           # raw/analysis/age_curves.json
python check_survivorship_bias.py    # raw/analysis/survivorship_check.json
```

### 병역 공백 발견 (사용자 관찰) + 전체 1차/2차 스탯 확장

사용자가 생존율 절벽(25~26세 43%)의 원인으로 병역을 지목 - 국내선수 경력 데이터에서 "시즌코드가
2 초과로 건너뛰는 공백"을 세어보니 실제로 176건 중 **62.5%(110건)가 23~26세에서 시작**(24세가
최다, 42건), 공백 길이는 대부분 시즌 1개 분(111건) - 상무(연 10명 안팎)를 못 가면 일반 입대로
1~2시즌을 통째로 비우고, 그중 상당수는 복귀해도 로테이션에 못 돌아온다는 것과 정확히 부합.
생존율 급락의 상당 부분이 이 병역 시점과 겹침.

이어서 COUNTING_STATS/RATE_STATS를 3개(astRt/dk/per)에서 **1차/2차 스탯 전부**(득점/리바운드/
어시스트/스틸/블록/덩크/3점슛/자유투/야투/턴오버/파울 + PER/PIE/사용률/어시스트율/턴오버율/
리바운드율/유효슛%/트루슛%/**공격효율/수비효율**/공격·수비리바운드율/AST-TO/어시스트비율)로
확장. 핵심 발견: **수비효율은 세 포지션 다 23~25세로 이른 나이에 정점**이고 이후 계속 나빠짐
(스틸/블록 이른 정점과 같은 결 - 순발력 의존도가 큼). 공격효율은 가드만 26세로 조금 늦고
포워드/센터는 21~22세로 이름(림 근처 마무리가 초반 강점). 경계나이(21세/38세) 피크는 "정점"이
아니라 "관측범위 안에서 아직 안 꺾인 추세"로 해석해야 함(포워드 3점슛/어시스트비율 등).

## 나이곡선 실제 피처화 (2026-08-20, "조심스럽게 피처화해서 테스트")

   선수가 이렇게 성장할 것"이 아니라 "이 나이대는 그 포지션 전형적으로 어느 수준"이라는 서술적
   컨텍스트로만 사용(팀 로테이션 출전시간 가중, leak-free). **잔여 누수 주의**: age_curves.json

   "전형적 정점"을 쓰게 됨 - 다른 피처들보다 약하지만 완전히 leak-free는 아님(docstring에 기록).
2. **로스터 연속성** - 직전 완결 시즌 상위 8명 로테이션(출전시간 가중) 중 이번 시즌 윈도우에도
   남아있는 비율. 병역/트레이드/부상 등 원인은 구분 못 하지만 "핵심 선수가 없어졌다"는 신호
   자체가 유효한 전력변화 지표.

### 테스트 결과 - 둘 다 기본 피처셋에서 뺌 (2026-08-20)

전체 피처(73개)로 재튜닝하니 RandomForest가 64.3% -> 63.6%로 **오히려 떨어짐**. feature_importance
순위에선 `away_rosterContinuity`가 69개 중 9위로 꽤 높게 나와서 의아했는데, 하이퍼파라미터를
고정하고 피처셋만 바꿔가며 직접 애블레이션해보니 원인이 명확해짐:

| 구성 | 정확도 |
|---|---|
| 기존 최고(나이곡선/연속성 없음) | **64.3%** |
| + 로스터연속성만 | 62.2% |
| + 나이곡선만 | 62.9% |
| + 둘 다 | 63.6% |

**둘 다 개별로도 held-out 정확도를 깎아먹음.** RF importance(불순도 감소량 기준)가 높다고 실제
일반화 성능에 도움된다는 뜻이 아니라는 걸 보여주는 사례 - train셋 안에서 트리가 그 피처로
분기를 치긴 하는데, 그게 새 시즌(2025-26)엔 안 먹힘. `tune_hyperparams.py`의 기본
`FEATURE_KEYS`에서 둘 다 뺐고(64.3% 구성으로 복귀), 이유를 코드 주석에 남겨둠. 피처 자체는
`pregame_training_table.json`에 계속 만들어두니, 나중에 다른 모델링 방식(예: 트리가 아니라
선형모델+정규화, 또는 애초에 팀단위로 뭉개지 않는 방식)으로 재시도할 여지는 있음 - "이 방식
으론 도움 안 됨"이지 "완전히 무의미"라고 단정하는 건 아님(신체정보 피처 때와 같은 결론).

### Tier 02 - 다음(이벤트 시퀀스 스캔 필요)

`tools/build_tier2_stats.py` - 한 경기당 이벤트 스트림을 한 번만 훑으면서 5개를 동시 계산(효율을

  제외(전통적인 "샷 스트릭" 정의에 안 맞아서). 최고 기록 라건아 16연속 성공, 버논 맥클린
  15연속 - 둘 다 KBL 대표 효율형 빅맨이라 부합.
- **Quarter-by-Quarter Split**: 선수별 쿼터당 득점 비중, 총득점 12점 이상만 집계(노이즈 방지).
- **Triple/Double-Double Watch**: 5대 스탯(득점/리바운드/어시스트/스틸/블록) 중 2개 이상 8+

  `tripleDoubleConfirmedAt`)을 둘 다 기록 - 로드맵의 "8+ 실시간 알림"은 확정이 아니라 예고
  트리거로 해석. 15시즌 더블더블 5,438건 + 트리플더블 65건, 최고 라인 브랜든 브라운
  35/19/11/5/2.
- **And-1**: "215(파울자유투)가 직전 득점이벤트와 정확히 같은 시각(q,m,s)"이라는 첫 가설은
  300경기 샘플에서 1건만 맞아서 기각(로그 지연으로 초단위가 안 맞음). 대신 이벤트 인덱스 갭
  히스토그램으로 재검증(1~3에 뚜렷한 봉우리) 후 "같은 선수·같은 팀의 마지막 득점 후 3이벤트
  이내 + 그 사이 상대팀 득점 없음"으로 재정의. 리더보드 1위 오세근(35회), 2위 라틀리프(33회) -

## 5차 확장 - 10경기 비교 + 프리뷰/AI요약/차트 + 강팀 서사 (2026-08-24)

### 10경기로 확장 - 가장 위험한 리팩터링

`build_live_replay_demo.py`를 1경기 전용에서 `DEMO_GMKEYS` 리스트 기반 배치로 일반화. 전체
4207경기를 다시 스캔해야 하는 부분(마진 분포, WPA 랭킹용 리스트, 팀 넷레이팅 타임라인)은
**딱 한 번만 계산해서 10경기가 캐시로 재사용** - 그대로 10배 다시 스캔했으면 훨씬 느렸을 것.
선정 기준: wpa_biggest_plays.json 상위권(버저비터 7개) + 블로아웃 2개(43·45점차) + 2014~2026년
전 시즌대에 걸친 다양성. 최종 5.0MB(폰트 포함 전체 아티팩트는 더 큼, 16MB 한도 내).

프론트엔드는 `const GAME = ...`처럼 게임 하나에 고정됐던 최상위 상수들(GAME/timeline/N/
COMBO_DICTS/qBounds/wpFill 등)을 전부 `let`으로 바꾸고, 값 설정만 `loadGame(gameData)` 함수로
분리 - **함수 정의와 이벤트리스너는 전부 한 번만 실행**되게 유지해서 게임 전환할 때마다
리스너가 중복으로 쌓이는 버그를 피함(이게 이번 리팩터링에서 제일 위험했던 부분). 상단에
`<select>` 게임 선택기 추가. 검증: 10경기 전부에 대해 중간 지점 재생→선수모달→이벤트모달을
자동으로 돌리는 스윕 테스트까지 작성해서 콘솔 에러 0건 확인(연속으로 게임을 바꿔가며 테스트해서
이전 게임 데이터가 남아있지 않은 것도 확인).

### 버그 2건 + 전술 코멘트 + 비교표 재설계 + "역전 스토리" 내러티브 (2026-08-25)

사용자가 스크린샷 8장과 함께 지적한 문제들:

- **버그: 50점차로 지고 있는데 "최고 활약"으로 뜨는 선수** - `gameWideTopPerformer`가
  팀 결과 무시하고 전체 Game Score 1위만 뽑던 게 원인. 마진 15점 이상 블로아웃이면 이기고
  있는 팀 로스터로만 후보를 제한하도록 수정.
- **버그: 같은 푸시 알림이 계속 옴** - `runHome >= 6` 같은 조건이 런이 6점에 머무는 동안
  매 틱(`stepForward`)마다 다시 매치되던 게 원인. `timeline[idx-1]`과 비교하는 rising-edge
  체크로 수정(값이 막 6을 "넘어서는 순간"에만 1회 발화).
- **비교 테이블 줄바꿈 문제** - 암묵적 CSS 그리드(`1fr auto 1fr`)로 셀들을 그냥 쌓아놨던 게
  원인이라 폭에 따라 줄바꿈이 들쭉날쭉했음. `<colgroup>` + `table-layout:fixed` +
  `white-space:nowrap`인 진짜 `<table>`로 재작성.
- **지금 손이 뜨거운 선수의 구체적 수비 지침** - `hotPlayerTacticalNote()` 신규: 그 선수가
  가장 많이 성공시킨 구역(골밑/45도/코너, 좌우 각도까지 `shotAngleLabel()`로 판정)을
  "OO 구역에서 N/M(P%) - 이 구역을 막아야 합니다" 문장으로 뽑아 핫/콜드 카드에 부착. 현재
  쿼터까지 누적으로만 계산(미래 데이터 누출 없음).
- **"역전 스토리" 자동 서사** - `renderComebackStory()` 신규: 경기 전체에서 승자 기준 최대
  열세 시점을 찾고, 그 시점부터 종료까지 박스스코어 델타(`boxDelta`)로 (a) 패자 쪽에서
  갑자기 조용해진 플레이메이커(어시 3개 이상 → 0개), (b) 승자 쪽 3점 폭발 선수, (c) 벤치에서
  나와 스틸/득점으로 흐름을 가져온 선수, (d) 승부에 쐐기를 박은 결정적 슛(WPA 스윙 최대 지점)을
  한 문단으로 조립. 열세가 10점 미만인 경기는 조용히 숨김(10경기 중 2경기만 해당 - 나머지는
  애초에 각본 있는 역전극이 없었음, 억지로 만들지 않음).
- **한글 조사(이/가) 문법 버그** - 자체 검수 중 발견: `"이(가)"`를 문자 그대로 붙이던 하드코딩
  때문에 "9점가", "성공이(가)" 같은 비문이 나오고 있었음. 받침 유무로 이/가·은/는을 고르는
  `josa()`/`iGa()`/`eunNeun()` 헬퍼를 추가해서 팀명·조사 대상 단어 끝 글자의 유니코드
  받침 여부(`(code - 0xAC00) % 28 !== 0`)로 판정하도록 전면 교체(5곳: 강팀/약팀 서사 2곳,
  강팀/약팀 상세 헤더 2곳, 역전 스토리 벤치히어로·쐐기슛 2곳). 팀명이 "KGC"처럼 영문으로
  끝나는 경우엔 받침 없는 쪽(가/는)으로 자연 폴백.

검증: `node --check`로 문법 검사 후, 로컬 HTTP 서버(단 raw 코드 조각엔 `<meta charset>`이
없어서 - 실제 배포시엔 Artifact가 씌우는 스켈레톤이 처리함 - 테스트용으로만 `<!doctype html><meta
charset="utf-8">`로 감싸서 서빙, 안 그러면 브라우저가 UTF-8 바이트를 Latin-1로 잘못 읽어
모지바케 발생) 10경기 전부 콘솔 에러 0건 확인. 역전 스토리는 실제 10경기 중 열세 10점 이상인
2경기(전주KCC 82:81 안양KGC, 울산 현대모비스 89:91 수원KT)에서 문장 끝까지 전부 정상 조사로
렌더링되는 것까지 텍스트 단위로 재확인.

### ESPN 게임 리캡 스타일 리디자인 (2026-08-25)

사용자가 ESPN 76ers-Celtics 경기 페이지 스크린샷 8장을 주고 "이런 디자인으로, espn의 디자인과
레이아웃을 참고해서" 요청. 기존 다크 모바일 중계 화면의 골격은 유지하되(라이트 테마는 이미
기본값이었음), ESPN 카드 언어로 주요 컴포넌트를 새로 추가/재설계:

- **팀컬러/약칭 시스템** - `build_live_replay_demo.py`에 `TEAM_META`(11개 tcode -> 약칭+컬러)
  추가. kbl.or.kr 팀 로고 경로가 여전히 안 열려서(4차 확장 때 이미 확인됨) 실제 로고 대신
  일반적으로 알려진 팀 이미지 기준 근사 컬러 - 공식 브랜드가이드 대조는 안 했음, 나중에 로고를
  구하면 이 매핑은 참고용으로만 남기고 교체 예정. 게임 로드시 `--home`/`--away` CSS 커스텀
  프로퍼티에 실제 팀컬러를 주입해서, 기존에 고정 오렌지/블루였던 모든 요소(슛차트, 승률 바 등)가
  자동으로 이 경기 팀 색으로 바뀜.
- **선수 실사진** - kbl.or.kr에 선수별 실사진이 있는 걸 발견(`players-photo/{pcode}.png`, 원본
  470x609). 다운로드는 명시적 사용자 확인 후 진행. 전체 로스터(185명)를 다 받으면 너무 커서,
  10경기에서 팀별 득점/리바운드/어시스트 1위로 실제 등장하는 선수만(40명) 범위를 좁혀 새 스크립트
  `embed_leader_photos.py`로 다운로드 -> 120px로 축소 -> JPEG 재인코딩(원본 PNG 그대로면 40명
  16MB, 축소 후 250KB) -> base64로 `players[pcode].photo`에 주입. 리더가 안 된 선수는 프론트에서
  등번호 원형 아이콘으로 자연스럽게 폴백.
- **Game Leaders 카드** - 득점/리바운드/어시스트 팀별 1위를 사진+스탯라인(FG/FT, OREB/DREB,
  TO)으로 나란히. 팀 전체 최고 활약(가드/앵커 무관 게임스코어 1위)이 아니라 카테고리별 리더라

  파울/최대리드(카운트 비례 바)를 ESPN처럼 좌우 대칭 바로. 박스스코어는 기존 이벤트 로그 재생

- **풀코트 팀 슛차트** - 기존 선수별 반코트 모달과 별개로, 양팀 전체 슛을 한 코트에 팀컬러로
