# 역대 기록(Record Book) 설계 — 1단계

- 작성일: 2026-10-08
- 상태: 설계 승인(1/2, 2/2) 완료 · 스펙 검토 대기
- 이 문서의 범위: **1단계** — 팀·선수의 쿼터/경기 최다·최소 기록 + 라이브 알림 + 경기 후 AI 리포트

## 1. 배경과 목표

2026-10-07 부산 KCC 허훈이 S49G01N9 1쿼터에 9어시스트를 기록해, 방송이 "기존 한 쿼터 8개"라고 한 기록을 경신했다.
NBA 중계처럼 이런 특이 기록(역대 TOP10 안에 드는 쿼터·경기 기록)을 **라이브 중계에서 우리 사이트가 정확하게** 알리고,
경기 후 AI 리포트에도 싣는다.

요청 원문 요약:

- [팀, 10위까지] 쿼터별 최소/최다 득점, 경기 최다/최소 득점, 무득점 최장 시간, 야투 성공·실패 최다, 야투 연속 성공·실패 최다,
  쿼터별·경기별 리바·어시·블락·스틸 최다
- [선수, 10위까지] 쿼터 최다(득점·어시·스틸·블락·리바 등), 경기 최다, 한 경기 야투 연속 성공/실패, 여러 경기에 걸친 연속 성공/실패
- [이외] NBA식 특이 기록(퍼펙트 야투, 5x5, 최대 역전승, 최장 득점 런, 듀오, 트릴리언 클럽 등)
- 추가 요구(2026-10-08): 쿼터 기록은 **쿼터별(1Q·2Q·3Q·4Q)로 분류**하고 **쿼터를 묶은 전체 기록**도 함께 둔다. **연장전 보드**도 추가한다.

단계 분해:

| 단계 | 내용 | 상태 |
|---|---|---|
| 1 | 팀·선수 쿼터/경기 최다·최소 + 라이브 알림 + 경기 후 리포트 | **이 문서** |
| 2 | 경기 안 야투 연속 성공/실패, 무득점 시간(가뭄) | 후속 |
| 3 | 여러 경기에 걸친 연속 기록 | 후속 |
| 4 | NBA식 특이 기록(5x5, 퍼펙트 야투, 최대 역전승, 듀오 등) | 후속 |

## 2. 데이터 검증에서 확인된 사실 (설계의 근거)

데이터 위치: `raw/games/<gmkey>/{meta,player-stat,team-record,text-cast}.json` (5,696경기). 로컬 SQLite에는 경기 이벤트가 없다.
Supabase `game_events`는 같은 text-cast를 이관한 것이다.

1. **중계 이벤트(text-cast)는 옛 경기에서 공식 기록과 어긋난다.** 이벤트로 계산한 쿼터별 팀 득점이 공식 쿼터 점수(`meta.teamrecords`)와 일치하는 경기 비율:
   2006-07~2008-09 시즌 45~75%, 2009-10~2017-18 시즌 92~99%, 2018-19 시즌 이후 거의 100%(전체 92.1%).
2. 어긋난 경기를 그대로 쓰면 오보가 난다. 검증 없이 계산한 쿼터 어시스트 역대 상위는 김승현 11개(2007-03-23)와 이정석 9개(2013-02-19)가
   허훈 9개보다 앞서지만, 공식 박스는 김승현 11개(이벤트 15개)·이정석 10개(이벤트 12개)로 이벤트가 중복·과다였다.
   반면 허훈 2020-02-09 21어시스트는 공식과 정확히 일치한다.
3. 검증(§5)을 적용하면 쿼터 어시스트 1위는 허훈 9개(2026-10-07), 직전 최고 8개 6건이 공동 2위(문태종 2010, 박지현 2011, 이정현 2019,
   허훈 2020, 마레이 2025, 박지훈 2026)로 나와 방송의 "기존 8개"와 일치한다.
4. 이벤트 정의는 공식 팀 합계와 맞춰 확정했다(2019-20 이후 3,864팀경기): 팀 리바운드 = 선수 귀속 공격(209)+수비(210) 100.0%
   (팀 리바운드 218을 더하면 3.3%라 제외), 어시스트(211)·스틸(212)·블락(213)·3점 성공(205) 100.0%, 득점 99.9%,
   야투 성공/시도(201·205·207 / 202·206·208) 99.7%.
5. 연장 경기의 공식 쿼터 점수는 `teamrecords.<side>.scoreeq`(연장별 점수 배열), 이벤트의 연장 구간 라벨은 `X1`, `X2`, `X3`이다.

## 3. 범위

포함: §4의 93개 보드, Supabase 테이블, 전체 빌드와 경기 종료 시 증분 반영, 라이브 알림·패널, 경기 후 리포트 섹션.

제외(YAGNI): 연속·가뭄·멀티스탯·듀오·나이 기록(2~4단계), 역대 기록실 전용 페이지, 정규시즌/플레이오프 분리 보드, 선수 프로필의 기록 표시,
경기 전 "이만큼 하면 기록" 문구(기존 기록 도전 패널과 별개로 후속).

## 4. 기록 정의

### 4.1 보드와 구간(bucket)

- 보드 키 = `대상.단위.종목.방향` (예: `pq.ast.max` = 선수·쿼터·어시스트·최다). 대상 `p`(선수)/`t`(팀), 단위 `q`(쿼터)/`g`(경기).
- 구간: `Q1` `Q2` `Q3` `Q4` `OT` `ALL`(쿼터 보드), `G`(경기 보드).
  - `ALL`은 **1~4Q를 묶은 전체**(연장 제외)이며 테이블에 따로 저장하지 않고 Q1~Q4 항목의 합집합으로 계산한다.
  - `OT`는 연장 구간 하나(X1, X2, X3 각각)를 한 단위로 센다. 연장은 5분이라 `ALL`에 섞지 않는다(최소 기록이 전부 연장으로 채워진다).
  - 팀 득점 `최소` 보드는 `OT`를 만들지 않는다(0점이 흔해 기록이 아니다).

### 4.2 종목과 보드 수

| 대상 | 단위 | 종목 | 방향 | 구간 | 보드 |
|---|---|---|---|---|---|
| 선수 | 쿼터 | 득점 pts·리바 reb·어시 ast·스틸 stl·블락 blk·3점 tpm·턴오버 to | 최다 | Q1~Q4, OT, ALL | 42 |
| 팀 | 쿼터 | 득점 pts | 최다 | Q1~Q4, OT, ALL | 6 |
| 팀 | 쿼터 | 득점 pts | 최소 | Q1~Q4, ALL | 5 |
| 팀 | 쿼터 | 리바·어시·스틸·블락 | 최다 | Q1~Q4, OT, ALL | 24 |
| 선수 | 경기 | pts·reb·ast·stl·blk·tpm·to | 최다 | G | 7 |
| 팀 | 경기 | 득점 pts | 최다·최소 | G | 2 |
| 팀 | 경기 | 야투 성공 fgm·야투 실패 fgmiss·3점 성공 tpm·리바·어시·스틸·블락 | 최다 | G | 7 |
| | | | | **합계** | **93** |

저장되는 보드는 `ALL`을 뺀 80개다. 3점·턴오버는 "등등"의 해석이며 빼려면 종목 표에서 지우면 된다.
턴오버는 불명예 기록이므로 알림 문구에 "불명예"를 붙여 구분한다.

### 4.3 대상 경기

정규시즌·플레이오프·챔피언결정전의 종료된 경기를 합산한다(플레이오프 여부는 항목에 표시). 오픈매치·올스타 등은 제외한다.
경기 보드는 연장을 포함하고 항목에 `is_ot`를 표시한다.

### 4.4 순위와 TOP10

- 순위는 **공동 순위(competition ranking)**: `순위 = 1 + 그 값보다 더 좋은 항목 수`. 최다는 값이 클수록, 최소는 작을수록 좋다.
- TOP10 = 순위 ≤ 10(동률이면 10위를 넘어 항목이 더 포함될 수 있다). 표기는 "공동 N위"이고, 신기록은 종전 1위를 넘어선 경우(최소 보드는 밑돈 경우)이며 종전 기록을 함께 적는다.
- 보드·구간마다 순위 ≤ 15인 항목만 보관한다(기록이 깨져 밀려나도 TOP10 판정이 틀리지 않게 하는 여유).

### 4.5 종목의 이벤트 정의

| 종목 | 이벤트 코드 |
|---|---|
| pts | 201(2점)·207(덩크) = 2, 205(3점) = 3, 203(자유투) = 1 |
| reb | 209 + 210 (선수 귀속분만, 팀 리바운드 218 제외) |
| ast / stl / blk / to | 211 / 212 / 213 / 214 |
| tpm | 205 |
| fgm / fgmiss | 201·205·207 / 202·206·208 |

팀 종목은 같은 코드를 그 팀의 이벤트(`t` = 팀 코드)에 적용한다.

## 5. 검증 게이트

**공식 자료로 만드는 보드는 이벤트에 의존하지 않는다(2006년부터 전 경기):**

- 선수 경기 보드 = `player-stat.json` `records` (score, rb, ast, stl, bs, threep, to)
- 팀 경기 보드 = `team-record.json` `records` (score, fgt, fgtA → fgmiss = fgtA − fgt, threep, rb, ast, stl, bs)
- 팀 쿼터 득점 보드 = `meta.json` `teamrecords` (`scoreq1..4`, 연장은 `scoreeq[k]`)
  - 단, 그 팀의 쿼터 점수 합(+ 연장)이 팀 최종 점수와 같을 때만 쓴다. 2009-01-21 S13G01N167은 연장 점수 배열이 양 팀 똑같이 `[6,9,13]`으로
    잘못 들어 있어(공식 팀 기록은 135-132, 경기 메타로는 113-113) 합이 안 맞는다. 5,682경기 중 이 한 경기뿐이다.

**이벤트로 만드는 보드**(선수 쿼터 전 종목, 팀 쿼터 리바·어시·스틸·블락)는 두 관문을 모두 통과한 값만 후보가 된다:

1. 경기 관문: 양 팀의 이벤트 기반 Q1~Q4 득점이 공식 `scoreq1..4`와 같고, 연장이 있으면 연장별 이벤트 득점이 `scoreeq[k]`와 같다.
2. 항목 관문: 그 선수(또는 팀)의 그 종목 **경기 전체 이벤트 합계**가 공식 합계와 같다(선수 ↔ `player-stat`, 팀 ↔ `team-record`).

연장 구간 라벨이 `X1`~`X4`가 아니면(예: 아직 데이터에 없는 `EQ*`) 그 경기의 연장 후보는 만들지 않는다.
관문을 통과하지 못한 경기·항목은 기록 후보에서 빠진다(기록을 놓칠 수는 있어도 틀린 기록을 만들지 않는다).
이름 → pcode는 같은 경기 `player-stat.json`(pname, tcode)로 풀고, 같은 팀에 동명이인이 있으면 그 경기의 선수 보드를 건너뛴다.

## 6. 저장소 (Supabase)

새 테이블 1개. 서버(서비스 키)만 읽고 쓴다 — RLS를 켜고 정책은 만들지 않아 익명 접근이 막힌다.

```sql
create table record_entries (
  board        text not null,      -- 'pq.ast.max'
  bucket       text not null,      -- 'Q1'..'Q4' | 'OT' | 'G'
  gmkey        text not null,
  subject      text not null,      -- pcode(선수 보드) / tcode(팀 보드)
  period       text not null,      -- 쿼터 보드: 'Q1'..'Q4','X1','X2','X3' / 경기 보드: ''
  value        integer not null,
  game_date    date not null,
  game_start   text not null default '',   -- 'HH:MM' (같은 날 경기 순서)
  season_name  text not null,
  category     text not null,      -- 정규시즌/플레이오프/챔피언결정전
  subject_name text not null,
  tcode        text not null,      -- 소속 팀(팀 보드면 subject와 같다)
  opp_tcode    text not null,
  is_ot        boolean not null default false,
  primary key (board, bucket, gmkey, subject, period)
);
create index record_entries_board_idx on record_entries (board, bucket, value);
alter table record_entries enable row level security;
```

- 예상 크기: 80보드 × 15위(동률 포함) = 수천 행 미만. 전체 빌드는 행 수가 20,000을 넘으면 중단한다(정의 오류 방지).
- 롤백: `drop table record_entries;` + 정산 훅 제거(`tools/rollback_record_book.sql`).
- 기록의 "그 경기 이전 기준"(as-of) 순서 키 = `(game_date, game_start, gmkey)`.

## 7. 파이프라인 (Python)

- `tools/record_book.py` (라이브러리 + CLI)
  - `--rebuild`: `raw/games` 전체를 읽어 후보를 만들고 보드·구간별 순위 ≤ 15만 남겨 한 트랜잭션에서 교체한다. 웹이 빈 테이블을 보는 순간이 없다.
  - `--gmkeys G...`: 그 경기만 반영. 트랜잭션 안에서 advisory lock → 그 경기 기존 행 삭제 → 후보 삽입 → 영향받은 보드·구간의 순위 > 15 행 삭제.
    같은 경기를 두 번(노트북·클라우드가 동시에) 돌려도 결과가 같다(멱등).
  - `--verify`: raw에서 다시 계산한 상위 15위와 테이블을 비교해 다르면 비정상 종료(월 1회 점검, 구현 직후 확인).
  - 끝나면 `cache_invalidate.revalidate(["records"])`로 웹 캐시를 즉시 비운다(실패해도 예외 없음).
- 정산 훅: `live_collector.reconcile_finished_game`의 이벤트 이관 성공 뒤 5번째 단계로 `record_book.py --gmkeys G`를 호출한다.
  타임아웃 300초, 실패는 로그와 결과 dict의 `record_book` 항목에만 남기고 `ok`에는 반영하지 않는다(정산·수집을 막지 않는다).
  `daily_batch.run_supabase_sync`가 어제 경기 목록으로 같은 호출을 한 번 더 해 누락을 복구한다.
- 노트북 수집기와 GitHub Actions 수집기가 같은 훅을 탄다(둘 다 `fetch_one_game(force=True)`로 그 경기 raw를 받은 직후라 필요한 파일이 있다).
- 수집기가 메인 작업트리에서 돌고 있어 직접 편집하면 즉시 운영에 반영된다. 그래서 수집기가 읽는 두 파일(`live_collector.py`, `daily_batch.py`)은
  복사본에서 편집·테스트해 통과한 뒤 같은 편집을 적용하고 곧바로 import를 확인한다(그 밖의 새 파일은 수집기가 읽지 않으므로 메인 트리에서 바로 작업한다).

## 8. 웹 (courtside-web)

### 8.1 서버: `lib/recordBook.ts`

`getRecordContext(game, boxPlayers?)` → `RecordContext | null`.

- null 조건: 대상 경기가 아님(§4.3), 경기일이 오늘로부터 60일 이상 과거(보관 범위 밖 순위 오류 방지), 테이블이 비었거나 조회 실패(`soft`).
- `record_entries` 전체를 페이지 단위(PostgREST 1,000행 제한)로 읽어 `cachedFn("recordEntries", ttl 600, tags ["records"])`로 캐시한다.
  조회 에러는 **던진다**(빈 배열을 캐시에 굳히지 않는다).
- 경기 G 기준(as-of)으로 `(game_date, game_start, gmkey) < G`인 항목만 보드별로 요약한다:
  `tops`(순위 ≤ 10 항목의 값, 좋은 순), `holders`(순위 ≤ 3 보유자의 이름·날짜·값).
  쿼터 보드는 구간별 + `ALL` 요약을 모두 만든다. 예상 전송량 약 15KB(압축 약 3KB).
- G가 종료 경기면 `validated`(테이블에 G의 행이 있는 `board|bucket|subject|period` 키 목록)를 함께 준다.
  없는 항목은 검증을 통과하지 못했거나 아직 정산 전이라 기록으로 주장하지 않는다.
  이후 경기가 순위를 밀어내 보관 범위(15위)를 벗어난 항목은 사라질 수 있다(드문 경우이며 60일 규칙으로 범위를 제한한다).
- `lib/cachePolicy.ts`의 `TAG`에 `records`를 추가한다.

### 8.2 엔진: `lib/records.ts` (순수 함수, 클라이언트 번들 가능)

- 입력: `RecordContext`, 이벤트(pcode, tcode, action_code, quarter, clock), 선수·팀 이름.
- 이벤트를 한 번 훑으며 `lib/boxEvents.ts`의 `applyBoxEvent`로 (선수·쿼터), (선수·경기), (팀·쿼터), (팀·경기) 누적을 갱신한다.
  화면 박스와 같은 규칙이라 어긋나지 않는다.
- 최다 보드: 값이 바뀔 때마다 `순위 = 1 + (tops 중 더 좋은 값 수)`를 계산해 TOP10 안이고 이전 순위보다 좋아지면 기록 이벤트(`RecordMoment`)를 만든다.
  신기록(1위, 종전 기록 초과) / 타이(1위 동률) / 공동 N위로 문구를 나눈다.
  쿼터 값이 해당 구간 보드와 `ALL` 보드에 모두 걸리면 한 이벤트로 합치고 두 순위를 함께 적는다.
- 최소 보드(팀 쿼터·경기 득점): 구간·경기가 끝나는 시점에만 판정한다(다음 구간의 첫 이벤트 또는 마지막 이벤트).
- 임박(패널 전용): 진행 중인 구간에서 현재 값과 상위 3위 기록 값의 차가 NEAR 이내일 때.
  초기값: 선수 pts 5·reb 2·ast 2·stl 1·blk 1·tpm 1·to 1, 팀 pts 6·reb 3·ast 2·stl 2·blk 1. 빈도 실측(§10-5)으로 조정한다.
- 종료 경기는 `validated`에 없는 기록 이벤트(moment)를 버린다. 라이브(진행 중) 경기는 전부 "잠정"으로 표시한다.
- 신기록(1위 초과)을 깬 뒤에는 순위 단계가 더 오르지 않아도 값이 오를 때마다 다시 알린다(예: 허웅 2026-02-02 3점슛 11개 -> 12개 -> 13개 -> 14개).

### 8.3 화면과 알림

- `components/MilestoneWatch.tsx`: 맨 위에 "🏆 역대 기록" 그룹(달성 + 임박)을 추가한다. 기존 통산 기록 그룹은 그대로 둔다.
- `components/GameReplay.tsx`: `records` prop을 받아 기록 이벤트를 `momentsByIdx`에 합쳐 기존 토스트 파이프라인으로 알린다.
  순위별 아이콘: 1위 🏆, 2~3위 🥈, 4~10위 🏅. 라이브는 문구 앞에 "잠정"을 붙인다.
- 문구 예:
  - 토스트(경기 이전 기준에서 8개가 6건 공동 1위일 때) 8번째 어시스트 — "🏆 허훈 1쿼터 8어시스트 — KBL 타이 기록(공동 1위)", 9번째 — "🏆 허훈 1쿼터 9어시스트 — KBL 신기록 (종전 8개)"
  - 패널 상세: "한 쿼터 어시스트 역대 1위(종전 8개: 문태종·박지현·허훈 외 3명)"
- 임박 예: "허훈 1쿼터 어시스트 7개 — 1개 더하면 역대 타이".

### 8.4 경기 후 AI 리포트

`lib/postgameReport.ts`에 "역대 기록" 섹션을 추가한다(기존 "기록 달성" 위). 같은 엔진을 **종료 경기의 최종 이벤트 + as-of 기록**으로 돌려 시각(점프 링크)을 얻고,
`validated`에 있는 항목만 쓴다. 검증을 통과하지 못한 경기는 이 섹션이 없다.

### 8.5 페이지 연결

`app/games/[gmkey]/page.tsx`가 기존 `milestonesPromise`와 나란히 `recordContextPromise`(soft)를 시작하고,
GameReplay와 `buildPostgameReport`에 넘긴다. 실패하면 이 기능만 사라진다.

## 9. 오류 처리 원칙

- 읽기 실패·테이블 없음 → 기록 UI만 사라진다(`soft`). 에러를 빈 값으로 삼켜 캐시하지 않는다.
- 쓰기(정산 훅) 실패 → 로그만 남기고 정산은 성공. 다음 날 06:00 복구 배치가 다시 반영한다.
- 검증 실패 → 그 경기·항목은 기록에서 제외(주장하지 않는다).
- 라이브 알림은 잠정이고 확정은 정산 후 검증을 통과한 항목뿐이다.

## 10. 테스트와 검증 계획

1. **파이썬 단위 테스트** (`tools/test_record_book.py`): 검증 관문(통과/실패 사례), 공동 순위, 순위 ≤ 15 보관·정리, 증분 반영의 멱등성,
   `ALL` 구간 합집합, 연장 구간 분리, 팀 득점 최소의 OT 제외.
2. **알려진 기록 단언**(전체 빌드 후 `--verify` + 테스트): 쿼터 어시스트 `ALL` 1위 허훈 9개(S49G01N9)와 공동 2위 8개 6건,
   팀 쿼터 득점 1Q 최다 41점(정관장 2023-11-21), 1Q 최소 2점(전자랜드 2021-01-01), 팀 경기 최다 135점·2위 132점(원주동부·서울삼성, 2009-01-21 S13G01N167 3차 연장 135-132)·3위 121점(KT 2018-03-02), 선수 경기 어시스트 21(허훈 2020-02-09).
3. **대조 테스트**: 실제 경기 20개 이상에서 파이썬 후보값과 웹 엔진의 쿼터·경기 누적이 같음(정의가 두 언어에서 어긋나지 않는 안전장치).
   작은 픽스처 JSON을 파이썬으로 만들어 vitest가 읽는다.
4. **실전 재현**: S49G01N9를 "그 경기 이전" 기록으로 재생해 8번째 어시스트에서 타이, 9번째에서 신기록 알림이 나오는지 확인한다.
5. **알림 빈도 실측**: 2025-26 시즌 전 경기를 as-of 기록으로 재생해 경기당 알림 수 분포를 본다. 평균 1개를 넘거나 상위 5%가 3개를 넘으면
   토스트를 순위 5위까지로 줄이고 나머지는 패널 전용으로 한다.
   **실측(2026-10-08, 2025-26 정규시즌 270경기를 "그 경기 이전" 기록으로 재생)**: 경기당 평균 0.55개, 중앙값 0, 상위 10%·5% 2개, 1개 이상 76경기(28%), 3개 이상 13경기(5%),
   최대 23개(허웅 51점·3점슛 11개 이상 경기 - 모두 실제 사건). 5위 이내만 세면 평균 0.25개. 기준(평균 ≤ 1, 상위 5% ≤ 3)을 만족하므로 **TOP10 전부 토스트**로 확정한다.
6. 웹 단위 테스트(엔진, 서버 요약, 리포트 섹션) + `tsc`/`eslint`/전체 vitest.
7. 배포 후 프로덕션에서 curl로 패널 데이터와 리포트 섹션을 확인하고, 접근 제어는 익명 키로 `record_entries`를 읽어 막혀 있는지 확인한다.

## 11. 배포 순서와 롤백

1. DDL 실행(실행 직전 사용자 확인) → `--rebuild` → `--verify`.
2. 워크트리에서 정산 훅 개발·테스트 후 메인에 반영.
3. 웹 코드 배포(테이블이 비어 있거나 없어도 기능만 숨김).
4. 프로덕션 확인.
5. 롤백: 정산 훅 제거 + `drop table record_entries` + 웹 코드 되돌리기. 다른 앱·기존 테이블에 영향 없음.

## 12. 사용자가 확인한 기본값

- 1단계는 "핵심 먼저"(쿼터·경기 기록). 연속·가뭄·NBA식 기록은 후속 단계.
- 저장은 Supabase 테이블 + 경기 종료 정산 연결.
- 3점·턴오버 포함, 정규시즌·플레이오프·챔피언결정전 합산, 연장 보드 추가, 쿼터별 + 전체 묶음 보드.

## 13. 이후 단계로 이어지는 지점

- 2~3단계(연속·가뭄): 같은 테이블에 보드를 추가하고 엔진에 "순서 누적기"(연속 횟수, 무득점 시간)를 추가한다. 여러 경기 연속 기록은 선수별 현재 연속 상태 테이블이 필요하다.
- 4단계(NBA식): 멀티스탯(5x5, 20-20), 퍼펙트 야투는 박스 기반으로 같은 파이프라인에서 만들 수 있고, 최대 역전승·득점 런은 공식 `maxContiScoreCn`(팀 최대 연속 득점) 같은 필드를 먼저 확인한다.
- 역대 기록실 페이지는 이 테이블을 그대로 읽으면 된다.
